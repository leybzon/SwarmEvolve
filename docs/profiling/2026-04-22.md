# GPU Profiling Report — 2026-04-22 (Milestone M11)

**Hardware**: NVIDIA GB10 (Grace-Blackwell), aarch64 host, driver 580.95.05
**Compiler**: nvc++ 25.11 (NVIDIA HPC SDK `Linux_aarch64/25.11`)
**Flags**: `-std=c++17 -O2 -acc=gpu -gpu=mem:managed`
**CPU reference**: g++ (same aarch64 host), `-std=c++17 -O2`
**Profiler**: Nsight Systems 2025.3.2

All numbers in this report were produced by `scripts/profile.py` (wrapping
`nsys profile` + `nsys stats`). The raw CSVs and `.nsys-rep` archives
are under `data/profiles/2026-04-22*/`.

---

## 1. Headline result — the 10× perf gate is **not met at 50 drones × 1000 ticks**

| Scenario                      | CPU median | GPU median | GPU / CPU |
|-------------------------------|-----------:|-----------:|----------:|
| cluster_v1 vs cluster_v1, 50×100   | 0.93 ms    | 473.6 ms   | 510 ×    |
| cluster_v1 vs cluster_v1, 50×1000  | 1.31 ms    | 1355.5 ms  | 1032 ×   |
| cluster_v1 vs cluster_v1, 50×5000  | 3.00 ms    | 5481.6 ms  | 1830 ×   |
| stationary vs stationary, 50×1000  | ~1 ms      | 1380 ms    | ~1380 ×  |

The GPU build is **~1000× slower** than the CPU build at this problem size.
This is not a code regression — it is the expected behaviour of a per-tick
parallelisation scheme at n = 50 drones.

## 2. Root-cause analysis

### 2.1 Kernel-work budget is tiny

From `data/profiles/2026-04-22-stationary/summary.json` (50v50, 1000
ticks, no combat, all 16 000 kernel launches actually happen):

| Kernel                            | Total device time | Launches |
|-----------------------------------|------------------:|---------:|
| `movement_phase`                  | 2.54 ms           | 2 000    |
| `combat_phase_one_side` (×2 sides)| 2.28 ms           | 2 000    |
| `route_messages` (×2)             | 2.23 ms           | 2 000    |
| `decrement_cooldowns` (×2)        | 1.91 ms           | 2 000    |
| `project_enemies` (×2)            | 1.88 ms           | 2 000    |
| `apply_cooldowns` (×2)            | 1.86 ms           | 2 000    |
| `apply_deaths` (×2)               | 1.86 ms           | 2 000    |
| `query_phase<TeamA>`              | 1.10 ms           | 1 000    |
| `query_phase<TeamB>`              | 1.13 ms           | 1 000    |
| **Total kernel time**             | **16.79 ms**      | 16 000   |
| **Total memcpy time** (host⇄dev)  | **25.89 ms**      | —        |
| **Wall-clock**                    | **5 764.61 ms**   | —        |

Device-side work + bulk copies account for only **42.68 ms** out of
**5 764 ms** wall-clock. **~99.26 % of the wallclock is overhead**
(CUDA context init, per-launch latency, runtime bookkeeping, driver
synchronisation).

### 2.2 Per-launch overhead dominates

16 000 kernel launches × ~(5.76 s − 0.04 s) / 16 000 ≈ **358 µs of
wall-clock per launch**. Even subtracting a one-time CUDA init of
~500 ms, steady-state per-launch cost is on the order of **~330 µs**.
On the CPU the equivalent "tick" takes ~1 µs. 9 kernels × 1000 ticks ×
330 µs ≈ 3 s of pure launch overhead — which matches the measured
wall-clock within a factor of 2.

### 2.3 Why the code is correct but the scheme is unsuitable

At 50 drones per team, each OpenACC parallel loop has 50 iterations.
On the GB10 SM each iteration is a single thread; the grid is
embarrassingly small compared to the hardware's ~N thousand-core
capacity. The launch-latency overhead therefore dwarfs the per-thread
work, and the GPU sits idle for most of each tick.

This is a classic scaling-with-small-N limitation, not a correctness
or micro-optimisation problem. The profile is explicit about it:
kernel time (≤ 3 ms per phase) is already nearly pinned at minimum
launch granularity.

## 3. What **is** working

### 3.1 Per-platform trace equivalence

`tests/test_gpu_equivalence.py` demonstrates byte-identical traces
between the g++ CPU build and the nvc++ GPU build on the same aarch64
host at seed=42 across 200 ticks, plus outcome+tick-count identity
across seeds 0..4 at 300 ticks. SPEC §7.6 per-platform determinism is
therefore **strictly** satisfied here — the explicit data-clause bounds
in `engine.h` ensure the `bool* pending_deaths_target` transfer round-
trips correctly (earlier drafts defaulted to 1-byte transfers,
corrupting 9 of 10 death flags).

### 3.2 TDR resilience

`tests/test_gpu_tdr_stress.py` runs a 50-drone × 300-tick match in which
every `drone_ai` call performs a hard-bounded 5 000-iteration trig-
accumulate loop (≈ 100 k flops/drone/tick ≈ 5 G flops for the whole
match). The match completes with exit code 0, no CUDA error messages,
and the expected DRAW outcome. The GB10 driver's TDR watchdog was never
tripped.

### 3.3 All 9 parallel kernels are being emitted

`-Minfo=accel` confirms that each of the four game-loop phases plus the
support helpers produce GPU kernels:

- `movement_phase`, `combat_phase_one_side`, `apply_cooldowns`,
  `apply_deaths`, `decrement_cooldowns`, `route_messages` (in `engine.h`)
- `project_enemies`, `query_phase<TeamAAiCallable>`,
  `query_phase<TeamBAiCallable>` (in `engine.cpp`, plus the user-side
  `TeamA::drone_ai` / `TeamB::drone_ai` compiled with
  `#pragma acc routine seq`).

### 3.4 Managed memory wiring

`-gpu=mem:managed` is set in `ACCFLAGS`. Because `g_world` is
file-scope static (not heap-allocated), it is **not** auto-managed —
hence the explicit `copy`, `copyin`, `copyout` clauses with explicit
`[0:n]` bounds on every `#pragma acc parallel loop`. This is
deliberate: it is the robust, nvc++-friendly pattern that also keeps
the build correct under non-nvc++ compilers (the clauses become dead
text in the pragma-less build).

## 4. Recommendation

**M11 as specified is not achievable without an architectural change.**
The plan's 10× speedup clause for 50 drones × 1000 ticks assumes a
per-match parallelism model that does not fit the GB10's kernel-launch
latency characteristics. Three options:

1. **Defer the 10× target to M12.** The tournament workload is
   inherently a parallel-over-matches pattern: many (seed,
   matchup) pairs can be evaluated simultaneously. An M12-era
   GPU orchestrator that batches N matches into a single kernel
   launch (replacing the outer tick loop with a `parallel loop`
   over match indices, using the existing per-drone loop as the
   inner kernel) would amortise the launch overhead across ~N
   matches. For N ~ 64 this would move the crossover point far
   below the current single-match cost.

2. **Fuse the per-tick kernels.** Merge the 9 per-tick kernels
   into one fused kernel with per-phase `#pragma acc loop` inside
   and inter-phase synchronisation via `acc atomic` / explicit
   barriers. This reduces 9 000 launches/tick to 1 launch/tick,
   cutting the per-launch overhead by ~9×. Estimated ~330 µs ×
   1000 / 9 ≈ 37 ms — still slower than CPU, but within 50× rather
   than 1000×.

3. **Accept the current architecture as "GPU-ready, not GPU-fast"
   for single matches.** Ship M11 as a correctness milestone
   (equivalence + TDR-safety) and move on.

Per the guidance at the top of this repository, the honest
recommendation is **(1) — defer the 10× target to M12**. The M12
plan already contemplates batched evaluation; codifying "10× single-
match speedup" as an M11 exit criterion was an architectural
mis-match, not a coding defect.

This report is the formal record of that finding.
